## N10.1 Perf budget as a gate (#219)

- PR #220.
- `scripts/e2e-perf.mjs`:
  - A **longest main-thread block** per moment: the longest Long Task
    (`PerformanceObserver('longtask')`, installed before the page loads) that started
    inside the moment, or the click handler's own time if that is longer. A block is how
    long the page could not paint or take a tap.
  - Named metrics (`titleMs`, `groundsMs`, `handoffMs`, `handoffBlockMs`, `skipMs`,
    `skipBlockMs`, `backToClubMs`, `weekMs`, `advanceCallMaxMs`, `advanceBlockMs`,
    `longestBlockMs`, `bundleGzKb`).
  - `--budget [file]` checks them against `scripts/perf-budget.json` and exits 1 when
    one is over. A metric the run never reached counts as over.
  - `report.json` and `report.md` (metrics, budgets, verdicts) next to `perf.json`.
- `qa.yml` has a new **`perf`** job on its own runner (nightly and on demand), so the
  timings aren't taken on a machine busy with the soak. Its summary is `report.md`. A
  dispatch can run one job alone (`only: perf` or `only: qa`).
- The checker (a separate reviewer) found that the gate could not fail the job: `cmd | tee
  log || status=1` took tee's status under the default `bash -e`. The soak and
  playthrough steps had the same bug, so a failed soak or playthrough also left the
  nightly green. `qa.yml` now runs every step with `shell: bash` (pipefail). Its other
  fixes:
  - the load → title block counted from the blank page's clock (now from the new page's
    origin);
  - Long Tasks not yet delivered are taken with `takeRecords()`;
  - the budget file is read before the run;
  - `--budget <any file>` works.
- Verified:
  - Through the workflow: a run on the GitHub runner with a deliberately tight hand-off
    block budget (100 ms) failed the perf step and the job (run 39356033783). A run with
    the checked-in budget passes (see the PR).
  - Locally, a tight budget file exits 1 and names the missed rows.
  - The playthroughs and the soak are untouched apart from pipefail.

## N10.2 The multi-week advance yields between weeks (#223)

- PR #225.
- `advanceUntil` is async. Each week is still one synchronous `advanceWeek()` under
  fast-forward, so no hook sees a half-run week. Between weeks it awaits the next paint
  (`requestAnimationFrame`, then a task), so the page paints and takes taps.
  - A second advance while one runs does nothing.
  - The stop rules (`advanceRules.ts`) and autosave are unchanged.
- HUD while a run is under way:
  - the Advance button reads **"Week n of 27…"**, styled as a tile, not a faded button;
  - the ▾ menu toggle gives way to an orange **Stop**. Stop finishes the week in hand and
    toasts "Stopped after n weeks: you stopped the advance.", the same toast as a rule stop;
  - the HUD root carries `data-advancing` for the e2e scripts.
- `e2e:perf`: a multi-week advance is timed from the click to the end of the run. One "to
  finals" run also times a tap on the Ladder made mid-run, from the touch's timestamp to
  its handler (`midAdvanceTapMs`). `advanceBlockMs` and `midAdvanceTapMs` are budgeted at
  2 s. `e2e:season`'s `advanceMenu` waits for the run to end (N8's file; noted in the QA log).
- Tests: one frame between weeks and none before the first; in progress only during the
  run; Stop after the week in hand with the toast; a second advance is a no-op; a stray
  Stop doesn't stop the next run; every week under fast-forward; a throwing week leaves
  nothing running and the next run works; a second run reports `busy`; the real frame
  wait with fake timers (one animation frame and one task per week after the first). All the earlier rule
  tests are unchanged apart from `await`.
